# Git Commit 规范

本文规定 smart_frame 的提交粒度、commit message 格式和 Review 信息。目标是让审查者只看提交说明就能理解：为什么改、实际改了什么、代价是什么、应重点检查哪里，以及改动是否验证过。

> 硬性前提：本项目任何 `git commit`、`push`、merge、cherry-pick 等写操作都必须先获得用户明确确认。符合本文格式不代表自动获得提交权限。

## 1. 原子提交

一个 commit 只表达一个完整意图，并且应当可以独立理解、验证和回退。

- 功能、重构、格式化、依赖升级尽量拆开；不要把“顺手清理”塞进功能提交。
- 代码、对应测试和必须同步的文档应放在同一个 commit，避免中间提交处于错误或不可构建状态。
- 不提交构建产物、缓存、真实凭据、个人配置、Agent 会话记录或无关文件。
- 提交前检查 `git diff --check`、变更范围、敏感信息和项目要求的验证命令。
- worktree 并行开发时，每个任务形成自己的原子提交；共享文件冲突由主协调者在集成阶段处理。
- 不使用 `--no-verify` 绕过检查，不用 `--amend` 或 force push 改写其他人已基于其工作的历史，除非用户明确要求。

## 2. 标题格式

采用 Conventional Commits 风格：

```text
<type>(<scope>): <目的>
```

`scope` 可省略。标题写“为什么/为了什么”，不要只罗列文件或动作；使用中文，代码标识符保留原文；建议不超过 72 个字符；结尾不加句号。

常用 `type`：

| type | 使用场景 |
|---|---|
| `feat` | 新增用户可见能力 |
| `fix` | 修复错误行为 |
| `refactor` | 不改变外部行为的结构调整 |
| `perf` | 性能优化 |
| `test` | 只新增或调整测试 |
| `docs` | 只修改文档 |
| `build` | 构建系统、依赖或打包配置 |
| `ci` | CI/CD 配置 |
| `chore` | 不属于以上类型的维护工作 |
| `revert` | 回退既有提交 |

推荐：

```text
feat(photo): 支持 NAS 与本地照片混合轮播
fix(voice): 避免 ASR 失败后状态机停在 processing
docs(agent): 建立多 Agent worktree 协作规范
```

不推荐：

```text
update
fix bug
修改 photo_service.dart
完成需求
WIP
```

## 3. 正文必填结构

除极小的纯拼写修正外，commit 正文必须包含以下五节。即使没有已知负面影响，也必须写“未发现”，不能省略。

```text
要做什么：
- <需求、问题或目标；解释为什么需要本次提交>

做了什么：
- <关键实现和行为变化>
- <测试、配置、协议或文档同步>

负面影响：
- <性能、兼容性、资源占用、行为变化、维护成本或回退难度>
- 未发现已知负面影响时，写：未发现；主要剩余风险是 <...>

Review 重点：
- <最需要审查的文件、函数、数据流或边界条件>
- <希望审查者确认的不变量和失败分支>

验证：
- `<完整命令>` → <结果>
```

五节的含义：

- **要做什么**：描述提交前的问题和期望结果，不要提前写实现细节。
- **做了什么**：只写实际已经落地的改动；不得把计划中但未实现的内容写成完成。
- **负面影响**：主动说明 trade-off，而不只是“风险可控”。至少考虑性能、内存/磁盘、网络、兼容性、用户行为变化、安全、维护复杂度和不可逆数据变化。
- **Review 重点**：为审查者缩小搜索范围，指出最容易出错或最需要判断的部分；不能只写“请 Review 全部代码”。
- **验证**：记录真实执行过的命令和结果；未执行的检查明确写“未执行 + 原因”，不得写成通过。

## 4. Review 重点怎么写

根据改动类型至少覆盖相关项：

| 改动类型 | Review 应重点确认 |
|---|---|
| 协议/状态 | 向后兼容、非法输入、所有客户端状态同步、协议文档与测试 |
| 配置 | 默认值、旧配置迁移、序列化往返、敏感字段、README/AGENTS 同步 |
| 异步/并发 | 重入、竞态、取消、超时、资源释放、失败后状态恢复 |
| 文件/缓存 | 路径安全、部分文件清理、容量上限、淘汰策略、磁盘失败 |
| 网络/NAS | 超时、认证失败、离线降级、代理影响、重试是否放大流量 |
| UI | 空状态、加载/失败状态、键盘行为、多窗口尺寸、状态更新时机 |
| 语音 | 状态机转换、降级路径、麦克风/KWS/ASR/TTS 资源生命周期 |
| 重构 | 外部行为不变、接口调用方完整迁移、测试是否覆盖关键不变量 |
| 依赖/构建 | 锁文件、三平台兼容、产物体积、许可证、回退方式 |

Review 重点应尽量带代码定位，例如：

```text
Review 重点：
- `PhotoService.fileFor` 的并发下载去重，确认失败 future 不会自引用或残留 `_downloading`。
- `applyNasConfig` 的 fire-and-forget 刷新，确认设置保存不会被 NAS I/O 阻塞。
- NAS 失败时仍保留本地列表，不能把离线错误传播到轮播主链路。
```

## 5. 完整示例

```text
feat(photo): 支持 NAS 照片按需缓存播放

要做什么：
- 在不阻塞本地相册的前提下播放 WebDAV 照片，并限制本地缓存占用。

做了什么：
- 引入 PhotoItem，合并本地文件和 NAS 引用列表。
- NAS 图片首次展示时下载到磁盘缓存，后续命中直接读取，并按 LRU 淘汰。
- 增加下载去重、失败清理、离线降级和预取下一张测试。
- 同步相册架构、配置和 NAS 状态文档。

负面影响：
- 首次显示 NAS 图片依赖网络，会增加磁盘写入和最高 500MB 缓存占用。
- NAS 断开时未缓存图片无法展示；本地照片和已缓存图片不受影响。
- 缓存键依赖远程路径，NAS 文件原地更新后可能短时间继续使用旧缓存。

Review 重点：
- `PhotoService.fileFor` 的并发下载去重及异常后的临时文件清理。
- LRU touch/淘汰顺序是否会误删当前正在展示的文件。
- NAS 失败是否始终静默降级，而不会清空本地照片或阻塞设置保存。

验证：
- `flutter analyze` → No issues found
- `flutter test` → 57 tests passed
```

## 6. Breaking change、Issue 与联合作者

- 存在不兼容变更时，在正文后增加 `BREAKING CHANGE: <迁移说明>`，并在“负面影响”中重复说明用户影响和回退办法。
- 有任务或 Issue 时，可在末尾增加 `Refs: #123`；只有确实关闭问题时才用 `Closes: #123`。
- `Co-authored-by` 只记录真实参与且同意署名的人。不要默认把 AI Agent、模型名或工具名写入标题、正文或 trailer；是否披露由用户决定。

## 7. 提交前检查清单

```text
[ ] 已获得用户对本次 commit 的明确确认
[ ] commit 只包含一个意图，没有用户的无关改动
[ ] 标题为 <type>(<scope>): <目的>，能够解释为什么提交
[ ] 正文包含：要做什么、做了什么、负面影响、Review 重点、验证
[ ] 负面影响不是空泛的“无”，Review 重点有具体代码或行为定位
[ ] 验证结果真实；未运行项已说明原因
[ ] git diff --check 通过，无凭据、缓存、产物或 Agent 会话记录
[ ] 代码改动已通过 flutter analyze 和 flutter test
[ ] 必须同步的协议、语音、配置或架构文档已更新
```

仓库提供了 [`.gitmessage`](../.gitmessage) 模板。可直接复制填写，或由开发者自行选择是否为当前仓库启用（Agent 不得擅自修改 Git 配置）：

```bash
git config commit.template .gitmessage
```

也可以使用临时文件准备多行 message，避免 shell 引号和换行错误：

```bash
git commit -F /tmp/smart-frame-commit-message.txt
```

准备 message 不等于获得提交许可；Agent 在执行命令前仍需再次确认用户已经授权。
